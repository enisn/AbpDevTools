# Run Command

The `abpdev run` command runs the solution in the current directory. It supports multiple solutions, multiple .NET applications, npm web applications, and DbMigrator projects. Application processes are owned by a centralized per-user runner so they can continue after the command detaches.

## Usage

```
abpdev run <workingdirectory> [options]
```

## Parameters

| Parameter | Description |
|-----------|-------------|
| `workingdirectory` | Working directory to run. Default: `.` (Current Directory) |

## Options

| Option | Shortcut | Description |
|--------|----------|-------------|
| `--watch` | `-w` | Watch mode - automatically rebuild on file changes |
| `--skip-migrate` | | Skip migration and run projects directly |
| `--all` | `-a` | Run all projects without prompting |
| `--no-build` | | Skip build before running |
| `--install-libs` | `-i` | Run 'abp install-libs' while running |
| `--skip-check-libs` | | Skip the `wwwroot/libs` check before running |
| `--graphBuild` | `-g` | Use /graphBuild for building |
| `--projects` | `-p` | Names or part of names of projects to run |
| `--msbuild-property` | | MSBuild property passed to every selected `dotnet run` process. Use `Name=Value`; repeat for multiple properties |
| `--configuration` | `-c` | Build configuration (Debug/Release) |
| `--env` | `-e` | Virtual environment name |
| `--retry` | `-r` | Restart an application when it exits |
| `--verbose` | `-v` | Show verbose application output |
| `--yml` | | Exact path to an alternate root YAML configuration |
| `--detach` | `-d` | Start the selected applications and return without opening the dashboard |
| `--help` | `-h` | Shows help text |

## Examples

### Run in Current Directory

```bash
abpdev run
```

### Run in Specific Path

```bash
abpdev run C:\Path\To\Projects
```

### Run in Release Mode

```bash
abpdev run -c Release
```

### Run All Projects Without Prompt

```bash
abpdev run -a
```

### Run in the Background

```bash
abpdev run --detach
```

The runner starts automatically when needed. Use `abpdev ps` to inspect all active contexts, `abpdev attach` to reopen the dashboard, and `abpdev stop` from the same directory to stop that context.

### Skip Migration

```bash
abpdev run --skip-migrate
```

Useful when you don't need to apply migrations.

### Watch Mode

```bash
abpdev run -w
```

Automatically rebuilds and restarts when source files change.

> Note: In watch mode, URLs cannot be printed because dotnet doesn't provide output.

### Run with Virtual Environment

```bash
abpdev run -e SqlServer
```

Uses the SqlServer virtual environment configuration.

### Run Specific Projects

```bash
abpdev run -p MyApp.Web.HttpApi.Host
```

### Run with ABP Library Installation

```bash
abpdev run --install-libs
```

Runs `abp install-libs` automatically while starting the application.

### Run with MSBuild Properties

```bash
abpdev run --msbuild-property UseMudBlazor=true
```

This passes `--property:UseMudBlazor=true` to every selected `dotnet run` process.

For a property that should apply only to one project in a batch run, place an `abpdev.yml` file beside that project file:

```yaml
run:
  msbuild-properties:
    UseMudBlazor: true
```

## Project Detection

AbpDevTools automatically detects these project types:

| Type | Detection | Default Behavior |
|------|-----------|------------------|
| .NET application | `.csproj` with sibling `Program.cs` | Runs with `dotnet run --project` |
| DbMigrator | Contains "DbMigrator" | Runs before applications |
| npm web app | `package.json` with `dev`, `serve`, or known web-server `start` script | Runs with the detected package manager |

Inside a git repository, detection only considers files that git lists: tracked files, including files in submodules, and untracked files that aren't ignored by `.gitignore`, `.git/info/exclude`, or your global git ignore file. Git doesn't list files inside nested worktrees or repositories, so folders such as `.claude/worktrees/*` don't show up as duplicate applications and DbMigrators. To run the applications of a worktree, run `abpdev run` inside that worktree. Outside a git repository, when git isn't installed, or when git lists no files for the directory (for example because the directory itself is ignored), the whole directory is scanned.

For npm apps, package manager detection uses the `packageManager` field when it is set to `npm`, `pnpm`, `yarn`, or `bun`. If the field is missing, it falls back to `npm`. Lockfiles are not used to choose the runner because they can be stale or generated by templates.

Npm apps run without interactive stdin while they are managed by `abpdev run`. This prevents dev servers such as Vite from consuming the same terminal keys used by the `abpdev` dashboard shortcuts and menus. Stdout and stderr are still captured and shown in logs.

## Centralized Runner and Dashboard

The centralized runner is always the process owner; `--detach` only controls whether the CLI stays attached to its dashboard. Without `--detach`, the familiar live status view remains the default.

Each context is identified by its canonical working directory and resolved root YAML path. This means `abpdev stop` affects only the applications selected from that same context. A repeated `abpdev run` reconciles the launch plan and does not start a second copy of an already-running application. If launch options or YAML changed, stop the affected application and run it again to apply the new plan.

Dashboard keys:

| Key | Action |
|-----|--------|
| `↑` / `↓`, `K` / `J` | Select an application |
| `A` | Toggle selected/all application logs |
| `R` | Restart the selected application with its current launch plan |
| `S` | Stop the selected application |
| `Ctrl+S` | Stop the entire context |
| `Q` / `Esc` | Detach while leaving applications running |

`Ctrl+C` from the dashboard opened by `abpdev run` stops that run context. `Ctrl+C` from a later `abpdev attach` only detaches. The runner exits automatically shortly after its final application stops.

See [Centralized Runner Commands](runner.md) for `ps`, `stop`, and `attach` usage.

Unknown `start` scripts are treated as ambiguous. They are available in interactive selection but skipped by `--all` unless explicitly selected with `--projects` or configured in `abpdev.yml`.

```yaml
run:
  npm:
    scripts:
      - web
      - start
```

## `abpdev.yml` Configuration

Use [`abpdev.yml`](../configuration.md) to define default project selection, run options, npm scripts, MSBuild properties, and environment variables. A solution-root file can configure all applications, while a nearer file can override launch settings for one project.

Without `--yml`, root configuration lookup starts in the working directory and continues through its parents. The nearest `abpdev.yml` is used. Files are not merged.

## Multiple Solutions

When multiple solutions exist in the directory:

```bash
abpdev run
```

You'll be prompted to select which solution to run.

## Troubleshooting

### Application Doesn't Start

1. Check that all dependencies are installed: `abpdev prepare`
2. Verify database connections in configuration
3. Check for port conflicts

### Port Already in Use

Use the `--projects` option to run specific projects, or stop other running applications.

### Missing Dependencies

Run `abpdev prepare` to install all required dependencies.
